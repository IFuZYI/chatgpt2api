# 异常账号恢复与禁用：以「自动路径能否救回」为状态分界

号池账号的四种状态（正常 / 限流 / 异常 / 禁用）中，**「异常」与「禁用」的
分界长期没有明确定义**：代码里「禁用」只有一个写入点（上游返回
`account_deactivated`），其余所有失效形态都堆在「异常」里，而「异常」
既没有终态出口，也没有可靠的恢复路径。

## 背景：三个互相独立的失效

改造前实测（号池 310 账号，异常 168）：

1. **封号识别漏在 MFA 步骤**。上游对被封账号返回
   `403 + code=account_deactivated`，但它出现在 `mfa/verify` 而非
   `password/verify`。后者认这个 code，前者只做通用兜底 →
   `mfa_verify_failed_403` → 被归类为「非确定性失败」→ 永不禁用、
   永远按 6 小时退避重试。
2. **首次 401 什么都不做**。`invalid_count<=1` 一律 defer，而 defer 的
   语义是「不删」，但它连「标异常」也跳过了。账号带着 `quota=0` 和
   401 继续以 `status=正常` 参与调度。
3. **166/168 个异常号没有 password**。重登在参数校验阶段就 skipped，
   而 skipped 不产生任何状态变更 —— 这批号永远停在异常，且每轮重试
   都立刻返回 `no_password`，白占风控预算。

此外还有两处结构性缺陷：`invalid_count` 在恢复成功后**从不重置**
（退避按历史失败次数计算，「首次失效不删」的保护被永久消耗）；
退避**没有抖动**（同批失败的账号在同一时刻齐发重试，watcher 每轮
只能挑出 1~19/168）。

## 决定

**以「自动路径还能不能救」作为「异常 / 禁用」的分界**，并把失败
分类提升为认证链路上的一等概念。

1. **状态语义**
   - 异常 = 还有救（补凭据、等上游恢复、密码重登），**参与**自动维护
   - 禁用 = 自动路径已判死，**终态**，不参与任何自动维护
   - 「禁用」**不等价于封号**：封号只是最常见成因，密码错、缺凭据
     同样会落到禁用或需人工标记

2. **失败分类（白名单式）**
   - 确定性失败 → 禁用：`account_deactivated`、`invalid_password`
   - 需人工 → 标 `needs_manual_reason` 并**停止重试**：
     `no_password` / `no_email`（补上就能救，不该禁用，但也不该反复试）
   - 非确定性 → 保持异常继续退避：地区限制、限流、状态失效、
     需 TOTP、网络错误、**一切未知码**

3. **判定抽成共用函数**。`accountDeactivatedSignals(code, message)` 在
   每个步骤的错误映射里调用，同时匹配 code 与 message（上游不同步骤
   的 code 不一致，message 更稳定）。

4. **defer 只保护它真正想保护的动作**。首次失效标异常 + quota 归零，
   但绝不删除；删除门槛保持原语义（更新前计数 ≥ 2）。

5. **成功路径必须清零**：`invalid_count`、`last_invalid_at`、
   `last_refresh_error`、派生标记（`needs_manual_*` / `disabled_*`）。
   一次成功的刷新/重登意味着之前的失效记录都已失去意义
   （RFC 9700 §4.14 的轮换语义：新凭据签发表明旧链路作废）。

6. **退避带 full jitter**（下半区间 `[delay/2, delay]`），保住
   「失败越多等越久」的语义，同时消除同批账号的重合点。

7. **重登并发保护**：`beginRelogin`/`endRelogin` 做账号级去重，
   `reloginMaxConcurrency=2` 限制全局并发。没有它时，刷新收尾与
   keepalive 收尾会同时对同一账号发起密码登录。

## 被否掉的备选

**备选 A：不引入「禁用」，用「异常 + 长退避」表达终态。**
否掉的原因：异常号会被 watcher 反复选中，一个真被封的号一天要花
4~6 次密码登录 + TOTP —— 对上游是最强的自动化信号，且这些尝试
**永远不会成功**。终态需要一个明确的、不再消耗预算的表达。

**备选 B：失败 N 次后统一禁用。**
否掉的原因：会误杀。地区限制（出口 IP 不在支持区域）、限流、网络
错误都可能在 N 次内连续发生，而账号本身完全健康。禁用必须是
**确定性失败**的结论，不能是「失败次数够了」。

**备选 C：缺凭据直接禁用。**
否掉的原因：缺 password 的号补上密码就能救，禁用等于切断唯一的
修复路径。改为「标 `needs_manual_reason` + 停止重试」：既不再浪费
预算，也保留了明确的修复入口。

**备选 D：keepalive 成功时也把异常合并回正常。**
暂缓：keepalive 只换 token，不验证账号可用性（换 token 成功不代表
`/me` 能通）。由刷新负责状态合并更准确。

## 后果

- 禁用是吸收态：刷新成功、keepalive、401 命中都不能把它改回其它状态。
- 禁用号与需人工号被统一排除出所有自动维护列表
  （`isAutoMaintainable`），整池刷新也不再包含它们。
- 手动重登永不禁用 —— 人工操作不该被一次失败判死。
- 实测效果：168 异常 → 72 禁用 + 10 异常 + 228 正常，自动收敛，
  日志逐条记录禁用原因。
- **未覆盖**：密码重登仍走全局代理、keepalive 走裸 client。出口
  一致性与本状态机正交，属于签名级改动，单独跟踪（见
  `docs/account-lifecycle.md` §7）。
