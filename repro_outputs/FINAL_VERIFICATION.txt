ROUND 3 — ADDITIONAL STABILITY FIXES
------------------------------------
[FIXED] Progress-sweeper goroutine had no panic recovery.
        A long-lived ticker loop (every maxAge/4 ≈ 90 min) called
        SweepStaleProgress unprotected. In Go an unrecovered goroutine panic
        terminates the WHOLE PROCESS. watcher / cleanupScheduler /
        backupScheduler all had recovery; only this one did not.
        Verified by injecting a panicking sweep: without recovery the test
        process dies with "panic: sweeper blew up"; with recovery the loop
        survives and runs the next round. Stop is now idempotent (sync.Once).
[FIXED] cleanup/backup schedulers swallowed panics silently (`_ = recover()`).
        The loop kept running but did nothing, with zero log output — the
        failure mode is "images pile up / backups stop" with no clue why.
        Both now log the recovered value.
[FIXED] Background image tasks ran with context.Background().
        upstream.Client sets TimeoutSec=0 deliberately (to avoid cutting long
        SSE), so every request's deadline comes from the caller's ctx. With
        Background, an upstream TCP hang meant the task goroutine never
        finished and the account slot stayed occupied forever.
        Added backgroundTaskContext (30-minute backstop, respects earlier
        parent deadlines).
[FIXED] Frontend conversation persistence produced unhandledrejection.
        persistConversation / updateConversation awaited saveImageConversation
        with no catch, and are awaited by 4 event handlers plus a polling
        callback. A failed local save surfaced only as a red console line —
        the user neither saw a message nor knew the edit was not saved.
        Three save points now try/catch + toast; 3 frontend tests added.
[DOC]   ADR-0009 gap table re-verified: 6 of 8 items were already fixed
        (progress eviction, editable-task retention, request body limit,
        atomic tag writes) and are now marked as such; 2 remain documented
        design trade-offs (no active task cancellation; backups unencrypted
        by default).

ROUND 4 — RESOURCE LEAK & DURABILITY FIXES
------------------------------------------
[FIXED] Image page polling kept running after the component unmounted.
        runConversationQueue uses `while (true)` whose only exits are
        "no loading tasks" or "10 consecutive errors". Leaving the page did
        not stop it: it kept hitting /api/image-tasks every 2 s until the task
        finished, and since React 18 no longer warns about setState after
        unmount the leak was completely silent. Added unmountedRef checked at
        the top of each iteration; 2 frontend tests lock the cancel contract.
[FIXED] PNG re-encode closed its file handle explicitly after png.Decode.
        png.Decode can panic on malformed input, skipping the Close — a batch
        compression of hundreds of images could then hit "too many open files".
        Changed to defer source.Close().
[FIXED] JSON storage never fsynced the parent directory after rename.
        POSIX rename only updates the directory entry in memory; on power loss
        the old file can be gone and the new one not yet durable — i.e. the
        entire account pool disappears. tmp.Sync() only covers file contents.
        Added a best-effort directory fsync (ignored when the filesystem
        returns EINVAL, as rename already succeeded). SQLite backend needs no
        change: it defaults to synchronous=FULL.

ROUND 6 — PERFORMANCE BASELINE & OPTIMISATION
--------------------------------------------
Added benchmarks for the four hot paths (text token pick, image slot acquire,
ProxyFor, maintainable-token listing) at 10/100/300/1000 account scales, plus
parallel variants to expose lock contention.

Optimisations (all verified by before/after measurement):

1. Text token pick — pooled candidate slice (was: one allocation per request)
     43825 ns/op  5400 B/op  1 allocs/op
   → 39911 ns/op     2 B/op  0 allocs/op
   Critical detail: the buffer MUST be `clear`ed before returning it to the
   pool. `s[:0]` only zeroes the length; the backing array keeps the token
   strings alive and the pool pins the previous pool's tokens forever. The
   first version of this change missed that and was caught by
   TestTextCandidateBufferClearedOnPut (reverting `clear` reproduces
   "底层数组[0] 仍持有 secret-token").

2. Image slot rotation — removed a double slice allocation
   (`append(append([]string{}, ...), ...)` allocated twice)
     67169 ns/op  12508 B/op  5 allocs/op
   → 60472 ns/op   9819 B/op  4 allocs/op

3. Image slot acquire — write lock downgraded to read lock
   `acquireSlot` guarded a READ-ONLY traversal with s.mu.Lock(), serialising
   every concurrent acquire. Measured parallel-slower-than-serial
   (80.3 µs parallel vs 60.5 µs serial) — the classic write-lock symptom.
   After RLock: parallel 55.9 µs (−30%). `cursor` is atomic.Uint64, so
   incrementing under RLock is safe.

Deliberately NOT optimised (documented in docs/performance.md):
- readyCandidateTokensLocked is not pooled — it runs under the lock and
  buffer borrowing across the locked region is hard to reason about.
- ListMaintainableTokens is not indexed — it runs once per watcher tick
  (default 5 min); 89 µs is irrelevant.

New: docs/performance.md records the numbers, the reproduction commands, the
optimisations with their evidence, and the reasoning for what was left alone.

SOAK TEST (310 accounts, single instance)
-----------------------------------------
Sequential load, 200 requests:
  goroutines 37 → 32 → 9      (settled back)
  fd         17 → 14 → 6      (settled back)
  heap       10.5 → 12.2 → 5.8 MB

Concurrent load, 50 in-flight × 20 rounds:
  heap peak 75.5 MB, goroutines 9, fd 6
  After 2 minutes: heap 4.18 MB, GC count 544 → settled
  RSS remained ~107-117 MB

VERDICT: no leak. Heap, goroutines and file descriptors all return to
baseline. RSS does not return to the OS — that is documented Go behaviour
(the runtime retains the heap), and it is why .env.example and deployment.md
now recommend setting GOMEMLIMIT when the container has a memory cap
(e.g. 256M container → GOMEMLIMIT=200MiB), so the GC gets more aggressive
near the limit instead of the container being OOM-killed.

ROUND 13 — BACKUP CHAIN (real S3 round-trip)
--------------------------------------------
Existing backup tests covered only scheduling and snapshot construction — the
upload/download path that actually loses data had never been executed against
a real endpoint, so a SigV4 mistake could not be caught.

[ADDED] TestR2ClientLiveRoundTrip — opt-in via TEST_S3_* env vars; performs
        upload → download → byte comparison → delete against any S3-compatible
        endpoint. Skipped by default so CI stays hermetic.

[FIXED] Running it against MinIO immediately returned HTTP 403.
        Root cause: `host()` hardcoded `<accountID>.r2.cloudflarestorage.com`
        while `overrideBase` only replaced the endpoint URL. SigV4 includes the
        host header in the canonical request, so a mismatched Host is rejected.
        In other words `overrideBase` was half-finished — any attempt to point
        the client at MinIO / LocalStack / another S3 provider would 403.
        Fixed by deriving the host from overrideBase when set.
        After the fix the full round-trip passes against MinIO.

Docs: docs/deployment.md backup section now tells operators to run this
self-check before deploying to a new environment.
